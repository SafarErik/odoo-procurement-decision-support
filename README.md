# Odoo Procurement Decision Support

Development foundation for a BSc thesis proof of concept: an explainable,
ERP-independent procurement decision-support system integrated with Odoo. The
accepted V2 system will evaluate suppliers with a Decision Tree, allocate orders
with MILP, support disruption scenarios, and provide human approval and snapshot
PDF export through a Python web frontend. The official task assignment is recorded
in the approved task sheet (2026-09-22, reference 423.589/25/140). The complete V2
workflow is not implemented.

**Current V2 implementation:** T13 supplies immutable one-product planning
contracts, explicit hard constraints, minimum-cost allocation and epsilon cost-risk
alternatives through an ERP-neutral solver port and a replaceable PuLP/CBC adapter.
The application entry point requires explicit context for externally supplied risk
coefficients; missing scores never become zero risk. Score validity must cover the
supplier's allowed quantities. T13 is merged in main at `ff8cc5b` (PR #15).
T14 adds an offline controlled Decision Tree pipeline, validated model reload,
actual tree-path explanations and a narrow ML-to-MILP contract demonstration.
All generated training/evaluation evidence is explicitly synthetic; scores are
uncalibrated quantity-independent planning exposure proxies. No V2 HTTP/assembler/UI
or approval/PDF path is implemented. See the
[T13 design](docs/T13_V2_MILP_DESIGN.md) and [handoff](docs/T13_HANDOFF.md).
Current T14 evidence and limitations are in [T14 handoff](docs/T14_HANDOFF.md).

## T14 controlled supplier evaluation

The offline `supplier_evaluation/` package prepares 240 explicitly synthetic
supplier-context observations, reuses the neutral T8 Expected Arrival KPI, fits
one bounded Decision Tree on 160 suppliers, and evaluates 80 later, disjoint
suppliers. It validates ordered finite features, cutoff and duplicate boundaries,
model/runtime versions and actual tree paths. The held-out set does not select
tree configuration. Synthetic receipts and labels are separate from observed
source-derived history; the trained controlled model rejects observed inference.

Using the existing project-local Python 3.11 environment, from the repository root:

```powershell
.\.venv\t13-check\Scripts\python.exe -m pip install -e ".[frontend,dev]"
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli generate
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli train
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli evaluate
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli infer
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli demo
# Equivalent complete regeneration, training, reload, evaluation and actual CBC run:
.\.venv\t13-check\Scripts\python.exe -m supplier_evaluation.cli reproduce
```

Generated receipt data, joblib/manifest and detailed JSON outputs stay in ignored
`.artifacts/t14/`; `--directory` selects another local output directory. `train`
saves and reloads the artifact; all later commands reload it without retraining.
Use only artifacts generated by this pipeline locally: joblib loading executes
trusted Python serialization, and a checksum does not establish authenticity.
The [design](docs/T14_ML_DESIGN.md) defines feature/label/mapping/quantity validity;
the checked-in [evaluation](docs/T14_EVALUATION.json) records measured controlled
results. The 98.75% synthetic holdout accuracy reflects an intentionally
constructed noisy labelling mechanism, with no real-world superiority claim.

The in-process bridge produces T13 `RiskCoefficient` and `ExternalRiskContext`
with exact supplier joins and complete allocation-range coverage. Quantity
independence is an explicit controlled exposure-proxy definition, not proof that
real delivery performance is independent of order size. The actual CBC example
compares a EUR 102 minimum-cost plan with a EUR 109 lower-exposure alternative
inside a 10% cost cap. API, live assembly, scenarios and V2 storage belong to T15.

**Implemented V1 baseline:** T0, the read-only T1 Odoo RFQ slice, the ERP-independent T2
Decision Core, and the narrow T3 decision API are implemented. T4 completed live,
read-only Odoo decision-input discovery. T5 installed the standard Purchase

validated Odoo comparison facts can be combined with explicitly supplied,
source-attributed hard MOQ and supplier-promised lead time while provenance stays
outside the Decision Core. The application can retrieve open RFQ summaries through
the existing public read-only ledger. Separately,
`POST /api/v1/procurement/decisions/evaluate` evaluates caller-supplied canonical
requirements, offers, and weights through the Decision Core. T12 now connects the
controlled comparison-case path to immutable case persistence through a separate
trusted-caller API. The original RFQ ledger and caller-supplied evaluation endpoint
remain available. There is still no decision UI or Odoo write operation. T7 completed
historical-performance discovery and controlled live
acceptance for one candidate, `delivery_schedule_adherence`. T7-S preserves a
separate, bounded, read-only projection identity while direct stock-model reads
remain denied. The four-scenario fixture passed with `33.33%` and sample size `3`, so
T7 is `GO — CONTROLLED LIVE SUBSET ACCEPTED`. T8 now implements the accepted metric
as contextual canonical decision data: an ERP-neutral history port and typed model,
a read-only Odoo adapter over the T7-S projection, deterministic application-layer
calculation, stable supplier attachment, and separate field provenance. Values are
withheld below sample size `3`; no zero or neutral value is substituted. AC-07 is
satisfied for this bounded vertical slice. T10 leaves the legacy WSM path unchanged
and adds only the separately selected policy described below. See
[the T7 spike](docs/spikes/odoo-historical-supplier-performance.md),
[fixture procedure](docs/T7_FIXTURE_SETUP.md), and [T7 handoff](docs/T7_HANDOFF.md),
plus the separate T7-S [design](docs/T7S_DESIGN_SECURITY.md),
[manual setup](docs/T7S_MANUAL_SETUP.md), and [handoff](docs/T7S_HANDOFF.md).
T7-S implements a bounded method-only projection, and both its focused security
contract and the controlled T8 vertical slice passed. See also
[the T6 design](docs/T6_DESIGN.md),
[T6 fixture procedure](docs/T6_FIXTURE_SETUP.md), and [T6 handoff](docs/T6_HANDOFF.md)
for the prior boundary and evidence, and [the T8 handoff](docs/T8_HANDOFF.md) for the
current runtime contract and verification record. T9 completed the isolated policy
evaluation in the [T9 design](docs/T9_SCORING_DESIGN.md) and
[T9 handoff](docs/T9_HANDOFF.md). T10 implements that accepted policy as a bounded,
internal, explicitly invoked Decision Core capability. History is normalized directly
as `value / 100` and activates only after MOQ filtering when every eligible offer has
usable history (`n >= 3`). Otherwise the wrapper returns the exact existing
two-criterion `DecisionResult` plus a deterministic inactive explanation. The three
versioned PoC profiles are `cost_focused_history_v1` (`0.60 / 0.25 / 0.15`),
`urgent_history_v1` (`0.25 / 0.60 / 0.15`), and `risk_averse_history_v1`
(`0.30 / 0.30 / 0.40`). Existing profiles and the public HTTP API remain unchanged.
See the [T10 handoff](docs/T10_HANDOFF.md).

T11 adds internal decision-case persistence without exposing a new HTTP route. It
stores immutable, versioned canonical-input, selected-policy, evaluation-result,
and provenance JSONB snapshots in PostgreSQL, then permits one atomic transition
from `evaluated` to a human final decision: accept the recommendation, override it
with an eligible offer and rationale, or record no award with a rationale. Exact
idempotent retries return the recorded decision; conflicting reuse fails closed.
Retrieval reconstructs the stored snapshot and never reruns scoring. The buyer
reference is caller-supplied attribution, not authenticated identity or
non-repudiation evidence. See the [T11 handoff](docs/T11_HANDOFF.md) and
[persistence development guide](docs/PERSISTENCE_DEVELOPMENT.md).

## Architecture

```text
Reflex frontend --HTTP--> FastAPI API --> application RFQ use case
                                               |
                                               +--> Odoo adapter --JSON-2--> Odoo

caller JSON --> FastAPI decision schemas --> application decision use case
                                             |
                                             +--> Decision Core --> explained result

Odoo facts + attributed supplemental terms --> application T6 assembler
                                                        |
                                                        +--> canonical input
                                                        +--> provenance manifest

dedicated non-internal T7-S caller --JSON-2--> guarded Odoo projection method
                                                    |
                                                    +--> bounded ORM evidence
                                                              |
                                                              v
ERP-neutral history port --> application KPI policy --> contextual canonical history
                                                       +--> separate provenance
                                                       +--> explicit T10 mapper
                                                               |
                                                               +--> opt-in historical scoring
                                                               +--> exact legacy fallback

Decision Core snapshots --> application persistence ports --> PostgreSQL adapter
                                      |                              |
                                      +--> human decision rules      +--> Alembic schema
                                      +--> no recalculation          +--> immutable JSONB

typed V2 input + external risk context --> application planning use case
                                                     |
                                                     +--> Decision Core planning/solver port
                                                                    |
                                                                    +--> PuLP/CBC adapter
```

The frontend has no direct Odoo or database access. The application contract is
ERP-neutral, while Odoo transport and payload mapping remain inside
`odoo_adapter/`. The Decision Core remains independent of Odoo, FastAPI, Reflex,
and database frameworks. Direct Odoo database access by this project is prohibited.

Create local configuration and fill both blank password values with separate,

## Decision evaluation API

The synchronous decision endpoint accepts only canonical data in its request body.
It does not query Odoo, read environment-specific business data, persist a result,
or perform any write operation. All decision-relevant numeric values are JSON
strings and are converted directly to `Decimal`; binary floating-point is not used.

```http
POST /api/v1/procurement/decisions/evaluate
Content-Type: application/json
```

```json
{
  "requirement": {"requirement_id": "REQ-1", "requested_quantity": "100"},
  "offers": [
    {
      "offer_id": "Offer A",
      "supplier_id": "Supplier A",
      "unit_price": "10",
      "lead_time_days": "10",
      "minimum_order_quantity": "50"
    }
  ],
  "profile": {
    "name": "balanced",
    "unit_price_weight": "0.5",
    "lead_time_weight": "0.5"
  }
}
```

HTTP 200 returns the requirement and profile, the first-ranked offer or `null`, all
eligible offers with their relative WSM scores and criterion contributions, and all
excluded offers with their failed constraints. Malformed request structure or
decimal syntax returns FastAPI's normal HTTP 422 validation response. Valid syntax
that violates a domain invariant returns HTTP 422 with code
`invalid_decision_input`. An all-excluded evaluation is a valid HTTP 200 result with
an empty ranking and no recommendation. The recommendation is decision support for a
human; it is not an automated supplier selection or purchase decision.

PostgreSQL has a container health check. Odoo's official image does not expose a
documented, image-level health command in this setup, so verify it through the web
UI and container logs after startup.

## Continuous integration

GitHub Actions runs two independent workflows on ephemeral Ubuntu runners:

- **Quality:** runs for every pull request, pushes to `main`, and manual dispatch.
  Its stable `quality` job performs the fast checks and validates the Compose model
  with temporary synthetic credentials. Python 3.11 installs required PuLP/CBC and
  explicitly runs the T13 solver and T14 training/reload/inference/MILP runtime
  gates; missing dependencies are failures. Hosted T14 results remain unverified
  until the changes are separately published and run.
- **Container and API integration:** runs only for relevant runtime paths on pull
  requests and `main`, plus manual dispatch. It starts Odoo's PostgreSQL, a separate
  disposable T11 PostgreSQL service, Odoo, and FastAPI; runs only integration-marked
  tests; verifies frontend compilation; and checks technical named-volume
  persistence. It provisions Node.js 22.22 for the locked frontend build
  dependencies. Superseded runs are cancelled.

The integration workflow is not browser-level E2E coverage. In particular,
`reflex export --frontend-only --no-zip` proves that the frontend compiles, not that
the running Reflex UI successfully communicates with FastAPI.

Configure branch protection manually after the `quality` job has run at least once:

1. In the GitHub repository, open **Settings**, then the applicable branch rule or
   ruleset for `main`.
2. Enable required status checks and select the check named `quality`.
3. Do not make `container-api-integration` required at this stage.

The workflows do not change branch protection, repository settings, or any other
remote governance configuration. They require no cloud account, deployment token,
or persistent Google Cloud or AWS environment.

## Troubleshooting

- **`podman` not found:** prepend `$env:LOCALAPPDATA\Programs\Podman` to the current
  shell `PATH`, or reinstall the Podman CLI with its `PATH` integration enabled.
- **No Compose provider:** activate `.venv`, rerun
  `python -m pip install -e ".[frontend,dev]"`, and check `podman compose version`.
- **Machine is stopped:** run `podman machine start podman-machine-default`.
- **Odoo waits for PostgreSQL:** inspect `podman compose ... logs db` and verify the
  three matching `POSTGRES_*` values in `.env`.
- **Database manager rejects the master password:** use `ODOO_MASTER_PASSWORD`, not
  the PostgreSQL password; recreate only deliberately disposable local volumes if
  this value changed after the first database creation.
- **Reflex says the backend is unavailable:** start FastAPI, confirm the health URL,
  then check `BACKEND_BASE_URL` in `.env`.
- **Frontend export reports no active Node.js version:** activate Node.js 22.22 or
  later before running `reflex export --frontend-only --no-zip`; CI configures this
  version explicitly.
- **Odoo is healthy in the container but localhost refuses the connection:** restart
  the Podman machine and inspect its Windows forwarding helper. The audited host had
  this Podman-machine proxy issue; a temporary localhost-only SSH tunnel was used for
  the host HTTP smoke test. Do not broaden the Compose bind address as a workaround.
- **Port conflict:** change `ODOO_HTTP_PORT`; for the API or frontend, stop the
  conflicting local process or use their runtime-specific port options.

## Limitations

All Odoo integration remains deliberately read-only. The public RFQ ledger is
limited to validated `purchase.order` summary fields; the internal T8 history path
uses only the separate bounded T7-S projection. The public decision API supports only
MOQ eligibility plus unit-price and lead-time criteria on caller-supplied canonical
input. T10 adds a separate internal opt-in Decision Core path for
`delivery_schedule_adherence`; it is not exposed through HTTP schemas or routes. T6
adds only a narrow hybrid assembly
path for a validated single-product comparison subset; it is not a generic or public
Odoo-to-canonical API. There is no automatic RFQ evaluation, pagination, retry
policy, write operation,
decision UI, API authentication/authorization, production persistence, public
historical-performance endpoint, currency conversion, or unrestricted historical
inventory mapping. The local PoC uses live-verified dedicated read-only identities.
T5 proved company-scoped read access to `purchase.order.line` and the standard
`purchase.order.purchase_group_id` comparison key without granting the integration
identity the alternatives feature group or direct access to grouping/agreement
models. A production Odoo-to-canonical adapter remains deferred because no validated
hard-MOQ source or authoritative supplier-offer lead time is available, and the
approved T6 solution therefore requires explicit, source-attributed supplemental
terms. The controlled three-RFQ T6 fixture and full read-only hybrid chain passed
their opt-in live contracts on 2026-09-19. This evidence validates only the bounded
local proof-of-concept subset and does not turn the internal assembler into an
automatic or production Odoo-to-decision pipeline. Do not assign broad Purchase or
Inventory roles as a shortcut.

T7 validated a candidate purchase-line-to-receipt chain and defined
`delivery_schedule_adherence` against Odoo Expected Arrival with a separate
completed-line sample size. T8 implements that exact controlled policy as contextual
canonical data, and T10 maps only its scoring-relevant fields into the opt-in core
contract. The original internal identity
remains unsuitable because it cannot read `stock.move` or `stock.picking` and
inherits `stock.move.line` mutations. T7-S instead provides a method-only,
non-stored projection with mandatory company, exact-line, date, and count bounds,
called by a separate non-internal identity. The T8 adapter uses only this method,
maps its fixed schema to ERP-neutral observations, and fails closed on inconsistent
responses. The security and controlled semantic contracts passed on 2026-09-20.
The metric is withheld rather than set to zero when fewer than three eligible lines
exist. T10's direct normalization and three profile weights are transparent PoC
policy choices, not empirical optimization or production validation. Missing or
withheld history for any MOQ-eligible offer deactivates history for the whole set; it
neither becomes zero nor excludes the offer. Odoo reads, KPI calculation, provenance

## T12 controlled decision-case API

The T12 application coordinator creates one immutable decision case from an explicit
Odoo `purchase_group_id`, source-attributed supplemental MOQ and supplier-promised
lead-time terms, an optional exact supplier purchase-line history selection, and one
named scoring policy. It reuses the T6 assembler, T8 bounded history acquisition,
T10 scoring paths, and T11 PostgreSQL UnitOfWork. It never writes to Odoo.

All three routes require `Authorization: Bearer <T12_TRUSTED_CALLER_TOKEN>`. This
shared PoC secret proves only possession by a caller; `actor_reference` is
caller-supplied audit text, **not an authenticated buyer identity**. An unset token
fails closed. Set `DECISION_DATABASE_URL` and apply Alembic migrations explicitly
before use; startup never creates the schema.

| Endpoint | Purpose |
| --- | --- |
| `POST /api/v1/procurement/decision-cases` | Assemble, evaluate, and atomically persist one case; canonical UUID `Idempotency-Key` required; first success `201`, exact replay `200`, conflicting reuse `409` |
| `GET /api/v1/procurement/decision-cases/{decision_case_id}` | Return stored snapshots only; no Odoo/history read or rescoring |
| `POST /api/v1/procurement/decision-cases/{decision_case_id}/final-decision` | Reuse the one-time T11 accept, override, or no-award rules; a separate canonical UUID `Idempotency-Key` is required |

Create requests accept only the named policies `cost-focused`, `urgent`, `balanced`,
`cost_focused_history_v1`, `urgent_history_v1`, and `risk_averse_history_v1`; there
are no HTTP-supplied weights. History is optional and requires explicit exact
purchase-line IDs for each comparison supplier plus an explicit UTC `window_end`.
The application derives the accepted 365-day window. Arbitrary supplier history
discovery is not implemented. Without history, a selected historical policy follows
the accepted exact legacy fallback. Decimal values are HTTP strings, and source
attribution records origin and observation time without certifying truth.

See [T12 design](docs/T12_DESIGN.md) and [T12 handoff](docs/T12_HANDOFF.md) for the
request shape, migration, limitations, and verification evidence. The existing
`POST /api/v1/procurement/decisions/evaluate` remains unchanged.
